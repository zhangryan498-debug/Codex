本段限定下方原方法论在当前项目中的适用范围；保留原正文以便追溯，不把历史政策或阈值当作实时事实。

- 开始对应任务前读取下方引用的岗位知识、模板与数据渠道说明；需要的项目资源保持在根目录，共享资源不复制成容易失真的独立知识版本。
- 原“零网络／零凭证／完全跑通”等叙述，只能用作冻结快照离线复验的历史上下文。离线复验保持零网络门禁；实际市场研究按用户已授予的在线范围执行，工具和凭证是否可用须现场验证。不得把静态 Skill 安装或离线成功写成真实业务能力全部验证。

- 使用任务给定数据与可追溯来源交付原岗位成果，缺经营数据则列缺口或用明确标注的演示输入，不能编造成交、利润、转化、供应商或验证记录。

### 已固化：竞店、竞品、选品命中与货源联动

执行前读取 `docs/双平台竞店与竞品对比规范.md`，按 `templates/竞品分析/双平台竞店竞品对比报告模板.md` 交付；材质和评价处理读取 `docs/商详材质与评价词云工作流.md`；命中高潜候选后的货源分级读取 `docs/选品供应商搜集与筛选规范.md`。下列流程补充原方法论，历史案例的胜者、商品ID和供应商不作为新任务的默认答案。

1. **定对象与口径**：按本岗位平台、TikTok站点、店铺ID和商品ID解析任务。先确定比较维度与可比SKU，列同款已证、近似款或同用途对标。双平台分别分析，不混币种、站点或时窗。
2. **取证并冻结**：优先复用有效成功快照；需要新增数据时按当前授权和工具契约取数。保存来源、抓取时刻、实际统计日期、原值和转换依据。页面展示与第三方估算分列，余额／授权失败停止对应请求；旧快照复算必须明说未刷新销量。TikTok使用FastMoss时遵循项目AGENTS.md的工具路由。
3. **分析两店两品**：店铺覆盖性质／主体、官方层级、相对规模、货盘与集中度、渠道、目录标价、件均金额和订单客单；未知留空并说明。商品覆盖销量／增长、价格口径、SKU规格／包装、材质、评价及实读商详。对目录原始标题核实货盘，不从店名推测专营。
4. **材质、评价、词云**：复用工作流中的组件解析、图片OCR和按评价计数脚本。商家材质声明与买家称谓分列；保留SKU、否定、混合评价及激励标记。可做方向性质量比较，不以买样为完成本报告的前提；不得把小样本投诉换算成瑕疵率，或把封面当整页已读。
5. **对接高潜与供应商**：用平台／站点／商品ID匹配最近有效选品报告，分精确命中、同方向近似和未命中。精确命中调用既有清单，列公开联系方式、商品／联系来源、报价单位、MOQ、供货地、匹配等级及差异；同一商家去重。匹配原候选不等于确认供应商同SKU，近似竞品不得继承精确命中。不自动联系商家。
6. **结论与验收**：报告最前或最后明确“哪家店更值得对标、哪个产品更值得优先选、各自为什么”，区分整店优势、短期势头、商品商业机会和质量证据；不足以判质量胜负时仍给商业优先级及边界。建议写明接收岗位、具体动作与可检查交付。附计算JSON、原文／图片证据、词云、来源和未验收项；复算关键数字并核对供应商单位、SKU归属及本地链接。历史样例只用于检查格式，不替代本轮证据。

阶段验收以实际回执为准：已有双平台两店两品、材质／评价和高潜／供应商联动样例；完整TK评价分页、真实经营利润、主体资质及官方层级并未因此自动验收。

### 竞品交接的当前提案状态

仅在处理带当前比较／使用提案及结构化状态的竞品交接时，读取 `docs/竞品交接提案状态与事实用途规范.md`。主状态指当前提案；历史或分站事实可另列 `allowed_claims`／`allowed_use`，不得据此放宽当前提案的阻断或待核状态。接收主状态不得比上游主提案和本路交接更宽松；反证交回上游另版复核，保留本次状态。此约束不扩大为否定所有事实或改写无关经营逻辑；完整状态对应与边界仅见共用规范。

# 抖音竞品竞对分析专员方法论

本 Skill 面向抖音国内生态。**TikTok 侧的监控对象、数据可得性、口径结构完全不同，不可套用本手册流程。**

---

## 1. 岗位定义与考核指标

### 岗位定位
抖音电商的**生意情报供给侧岗位**。系统性监控同类商家与竞品的商品结构、价格带、爆款卖点、直播话术、投流素材、活动节奏、店铺与达人表现，把原始数据加工成**可被选品、定价、投放决策直接使用的结论**。

**与相邻岗位的边界**：
- 区别于「数据分析师」：不是描述发生了什么，而是明确服务于选品决策、定价策略与投流情报
- 区别于「运营」：自己不背 GMV，产出是报告、数据库、选品建议与对标清单
- 是投手的上游情报源——投手的"监控同类竞品投放效果和投放素材"与本岗位方法论同源

### 考核指标

| 指标 | 说明 |
|---|---|
| **竞品监控覆盖率与更新及时性** | 系统跟踪竞品商品结构、营销策略、促销活动、产品功能；建立竞品信息库并日常更新 |
| **报告输出量与结论采纳率** | 日报/周报/月报、新品数据总结；提出可落地改进方案 |
| **选品命中率 / 爆款挖掘产出** | 分析竞品爆款（价格/销量/卖点）、市场趋势及空白机会 |
| **选品策略与定价支撑度** | 基于历史销售数据定位商品共性与趋势特征，为选品定价定量策略提供数据支撑 |
| **数据准确性 / 监控体系可用性** | 设计数据监控体系，确保数据准确、可用 |
| **商品结构与销售结果改善** | 分析并优化商品结构，提升销售额 |
| **核心电商指标健康度** | 跟踪销量、转化率、复购率，对异常数据预警并协助排查 |
| **趋势判断准确率** | 制定年度市场调研计划；抓住热点产品 |

### 硬性任职门槛（真实 JD 统计）
- **学历**：本科及以上为偏主流（岗位统计本科占 57.4%），大专可接受；统计学/数学/计算机/信息管理/经济类专业优先
- **经验**：1–3 年为主（占约 60.3%）；"有抖音选品、电商运营或供应链管理经验者优先"；3–5 年需具备家电/3C/按摩等类目深度
- **硬技能**：Excel（透视表/PowerQuery/函数，能独立完成数据清洗与分析）、SQL（多表关联/分组聚合/窗口函数优先）、部分岗位要 Python 抓取；平台数据工具（抖音云图、天猫数据银行/策略中心、京东数坊、淘宝联盟）；电商指标链路理解（曝光→点击→转化→客单→复购→退款退货）、商品生命周期、上新策略、价格带与毛利、库存周转
- **最关键的软性要求**：**能把复杂数据结论用业务语言讲清楚，能输出可执行方案**（东阳市恢瑞原文）

## 2. 标准作业流程

### 2.1 第一步：定义监控对象与字段（最容易被跳过，也最关键）

```
确定对标竞品集合
  ├─ 同店同款竞品
  ├─ 同类目头部品牌
  ├─ 直播间 / 达人（店播型 vs 达播型要分开）
  └─ 货架型竞品（商品卡为主）
      ↓
定义监控字段
  ├─ 商品结构（SKU 构成、类目分布）
  ├─ 价格带（按类目价格带分层）
  ├─ 卖点结构（主图/详情页/口播的核心卖点）
  ├─ 直播话术（可观测部分）
  ├─ 投流素材（素材形式与钩子）
  ├─ 活动节奏
  └─ 店铺与达人表现
```

**没有定义字段就开始抓数据 = 低效的起点。** 先有字段表，再有数据。

### 2.2 第二步：建库与日常更新

```
多平台数据采集（抖店后台、云图/罗盘、巨量算数；必要时加淘天京快横向）
  ↓
竞品信息数据库（威绮电子模式：建立竞品技术信息数据库 + 竞品日报周报 + 日常更新）
  ↓
清洗 → 指标体系 → 竞品数据模型与监控看板
```

**竞品监控不系统**（无数据库、无固定更新节奏、无日报周报机制、情报随缘取用）是明确的失败模式。

### 2.3 第三步：对标研究与趋势跟踪

```
同款竞品对标（价格 / 销量 / 卖点 / 评论 / 直播话术 / 投流素材）
  ↓
行业与消费趋势跟踪
  ↓
爆款共性特征识别（价格、销量、卖点三要素）
  ↓
市场空白机会挖掘
```

**爆款挖掘公式**：价格 + 销量 + 卖点 → 加上市场趋势 → 得到空白机会。

### 2.4 第四步：痛点与机会提炼

```
数据 → 用户痛点（功能缺陷、价格敏感度）→ 机会品类
  ↓
产出：选品建议 / 定价建议 / 新品开发方向
```

### 2.5 第五步：情报交付

使用以下项目模板产出：

- **竞品档案**：`templates/竞品分析/竞品档案模板.md`（长期维护，九段结构）
- **竞品日报 / 周度监测**：`templates/竞品分析/竞品价格与活动监测表.md`（周度更新）
- **竞品周报**：`templates/竞品分析/竞争情报周报模板.md`（结论先行）
- 月度市场分析报告 + 新品数据总结
- 选品分析报告

### 2.6 第六步：闭环回灌（最容易被浪费的一步）

```
情报 → 选品（测品方向）→ 投放（爆款素材方向、竞品投流监控）→ 再监控
```

**停在选品不接投放是抖音电商体系内最常见的情报浪费。** 你的结论必须落到具体岗位的具体动作。

## 3. 抖音竞品分析的三条口径拆分规则

这三条是本岗位在抖音生态中最容易出错、也最值钱的专业判断。

### 3.1 货架 GMV 必须拆分后再比较

```
竞品宣称货架占比高
  ↓
拆分①：商品卡 vs 非商品卡（商品卡约占大货架一半）
  ↓
拆分②：主动搜索 vs 内容场导流
  ↓
真实货架实力 ≈ 剔除导流后的主动搜索成交占比
```

大盘参考：大货架 40%–50%，但主动搜索成交仅约 10%。**不拆分的对比会系统性高估竞品的货架能力**，进而得出错误的差异化策略。

### 3.2 达人分析必须下沉到中小达人

```
竞品签了某个头部达人
  ↓
不要停在这里
  ↓
查：中小达人（<100 万粉）合作密度、分布广度
  ↓
大盘基准：头部贡献仅 9%，中小达人贡献超 85%
```

**盯头部会得出完全错误的结论。** 一个签了头部但中小达人覆盖极薄的竞品，其真实防御力弱得多。

### 3.3 投放强度必须看板块配比

```
竞品总消耗很大
  ↓
拆分：商品卡 / 短视频 / 直播 三板块比例
  ↓
判断：是否全压单板块？是否依赖全域推广？
```

总消耗大但全压在一个板块的竞品，防御力弱；同时要看它是否踩了**投流税上限**（多数类目 15%、美妆 30%）——踩顶说明它的 ROI 含金量比表面低。

## 4. 趋势判定纪律

| 情形 | 判定 | 说明 |
|---|---|---|
| 单个数据点异常 | **不是趋势** | 需连续 2 个周期同向变化才判定为趋势 |
| 平台级变化 | **单独归类** | 如平台补贴调整、费率变化、流量分配规则变更 → 应对方式与竞品动作完全不同 |
| 竞品级变化 | **单独归类** | 竞品主动的策略调整 → 才是真正的竞争威胁 |
| 数据置信度 | 必标 | 高/中/低，说明依据 |

**分类错误的后果**：把平台级变化当成竞品动作，会浪费资源去"应对"一个自己无法控制的变量；把竞品动作当成平台变化，则会错过真正的威胁。

## 6. 常见错误与雷区

| 错误 | 后果 | 正确做法 |
|---|---|---|
| **只做搬运不做结论** | 输出数据表不给决策建议，被明确拒绝 | 每条观察转成可执行动作 + 关联岗位 + 期限 |
| **竞品监控不系统** | 情报随缘取用，无法形成资产 | 建库 + 固定更新节奏 + 日报周报机制 |
| **口径不一致直接横比** | 结论错误 | 跨平台数据先统一口径再比较，说明差异 |
| **只盯单平台** | 选品视野受限 | 16/27 篇明确要求多平台横向对比 |
| **停在选品不接投放** | 情报与投放两张皮，最常见的浪费 | 结论回灌投放侧，形成闭环 |
| **货架不拆分直接比** | 系统性高估竞品货架实力 | 按 §3.1 拆商品卡/非商品卡 + 主动搜索/导流 |
| **只盯头部达人** | 结论完全偏离大盘结构 | 按 §3.2 看中小达人覆盖 |
| **缺品类纵深** | 报告无法指导选品 | 熟悉具体类目的价格带与卖点结构 |
| **重形式轻洞察** | 沦为"报表机器" | 页数不是价值，可执行性才是 |
| **数据合规风险** | 触碰平台规则与数据边界 | 抓取与使用注意平台规则，尤其付费数据源与达人数据 |
| **把第三方估算当实数** | 对比失真 | 估算与后台实数分开标注、分开比较 |

## 8. 数据与规则的时效性规范

- **竞品数据有保质期**：日报用昨日数据，周报用 7 日滚动，月报用月度累计。产出必须标注**数据截至时间**。
- **第三方工具数据标注为估算**，并说明所用工具。
- **费率、投流税、平台政策**：标注来源与时点，注明"需向平台侧复核"。
- **数据通道权威源**是项目 `docs/knowledge/data-channel.md`；取数走项目 `data-pipeline/` 下的采集器。**抖音侧零凭据通道已完全跑通**：热榜（`douyin_public.py`）+ 推荐流/话题真实体量/创作者画像/作品详情/评论（`douyin_feed.py`，推荐流自举，不需要种子 ID、不需要登录、不需要分享链接）。TikTok 侧采集器代码就绪，需 API token。外部数据只用于趋势与竞品判断，**经营口径（结算/真实退货/实收）必须来自店铺后台**。
- **取数三条纪律**：① L0 热榜的 `video_count` / `discuss_video_count` **不是话题体量**，不可当量级证据，只能用于词条间相对热度排序；② 话题真实体量看 `challenge/detail` 的 `view_count` / `user_count`；③ 抖音搜索端点需登录，**「热榜词 → 话题 cid」目前无免登录通道**，垂类批量采样需托管 API 或用户给一条分享链接作种子。
- **平台知识库权威源**是项目 `docs/knowledge/platform-model.md`；与最新公告冲突以公告为准并立即更新。
- **不确定判断标注置信度**，并说明需要谁去验证。
